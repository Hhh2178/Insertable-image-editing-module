## 用户原话与本轮范围

用户指定本仓库，要求：“那么基于我们这次的改动，你再分析下这个项目，有哪些可以进行补完补充”。原话中的开发机绝对目录按仓库相对路径规则省略。

本轮只做源码核查、本地隔离复现、现有检查及建议整理，不修改业务源码、公共接口、已确认 PRD 或模型配置，不调用真实模型，不提交/推送。以下是待讨论建议，不是已授权实施的正式需求。

## 结论

A+ 宿主为适配实测，已经自行实现通用模型调用、尺寸策略、提示词直接改写、任务快照与结果保存。独立模块仍主要提供原 Nano 合同及严格方案改写合同，A+ 当前复用的核心是画笔、笔迹解码/合成和编辑提示词；宿主成功接入不能证明独立模块完整服务已经具备相同能力。

建议优先把这些经过实测的通用能力补回模块，并保留宿主对模型路由、鉴权、任务持久化和版本存储的所有权。原来按 PRD 固定 Nano、严格方案校验的实现属于旧合同；扩展它们需要确认兼容方式，不能简单当作旧功能未完成。

## 建议一：修复返回解析与真实响应测试，P0

本地只读调用结果：

```text
data.result.images[0].url = "https://cdn.example/result.png" → 正常取到地址
data.result.images[0].url = ["https://cdn.example/result.png"] → undefined
```

这是明确可复现的缺陷，也与 A+ 此前“任务完成，但没有可用图片”的兼容问题一致。建议按有证据的响应路径处理字符串/数组，逐个验证候选 URL；不要任意递归提取整个响应里的链接，以免误拿输入图地址。无有效结果仍应失败并保留 taskId。

补充嵌套 URL 数组、多候选首项无效/后项有效、空数组、非法 URL 等回归。现有 adapter 测试标题虽提到 array URL，实际样例是 images 数组内的字符串 url，没有覆盖本次结构。

## 建议二：可配置模型与尺寸能力，P0

由宿主服务端注入模型、resolution、quality 及尺寸能力；浏览器仍只传原操作字段，不允许直接选择供应商或注入凭证。Nano 的原参数可以作为兼容预设，增加 GPT Image 2 与 Sunburst 的独立预设。

尺寸至少分为四个值：来源、请求、供应商实际返回、最终交付。建议提供纯尺寸解析/约束工具：按来源或固定画布请求，可声明 multipleOf、最大像素等限制；能力绑定供应商与具体路由，不把某一个供应商的限制推断为所有同名模型的通则。

A+ 已确认的编辑策略可作为推荐预设：来源 1916x821，上传不缩放，请求按能力对齐至 1920x816，最终保持 1916x821。普通生图/重生固定 1920x800 是 A+ 的业务选择，不应变成通用编辑模块默认值。

模块可导出“将给定结果字节等比适配到目标画布”的可选 Sharp 工具与尺寸报告；下载、授权、最终写盘仍由宿主负责。支持保持原字节、等比补边或拒绝尺寸偏差等显式策略，不隐式拉伸/裁切。

## 建议三：补充 prompt-only 指导模式，P0

增加独立模式：完整旧提示词 + 本轮指导 → 一次文字 LLM → 完整新提示词 → 生图。不要求 updatedPlan、summary 或业务方案校验，也不注入与修改意图冲突的默认人物设定锁。

保留原“方案与提示词一起修改”的严格模式，兼容依赖它的宿主。纯提示词模式可以接收完整纯文本，兼容已知旧 JSON 和代码围栏；仅在 JSON 已完整闭合、后续只有格式噪声时容错。截断 JSON、多份冲突输出或空内容不能猜成成功。

本地已确认：现有 parser 对完整纯文本、围栏 JSON 都报“不是有效 JSON”。这符合旧严格合同，但不满足 A+ 新工作方式。必要输入长度/非空、来源权限、任务状态边界保留；不要用取消全部校验替代模式划分。

## 建议四：公开任务句柄、恢复动作及幂等合同，P0

编辑 provider 当前只有 generate，taskId 仅存在函数局部变量。超时后宿主知道 submitted，却无法通过模块接口只查询原任务。建议提供 submit/poll 或 generate + onAccepted/resume 的可组合接口，返回可持久化的任务句柄，由宿主保存。

指导服务也应在调用生成器前持久化“运行中/受理未知”的边界，再由适配器回传明确受理状态。当前隔离复现：生成器尚在运行时，pending.submissionState 仍为 not_submitted；在没有宿主锁的情况下调用 retryGeneration，同一 operationId 进入生成器两次。这里不代表所有宿主都会重复提交：示例有部分入口去重，A+ 有自己的保护；需要把保护责任与接入要求明确化并用崩溃恢复测试覆盖。

不在模块里引入数据库或全局任务系统。由宿主实现按 principal/operationId 的持久化与原子占位；模块提供回调、状态约束和示例，区分重试提交、继续轮询、仅重试保存。HTTP 408/连接断开不能据此证明未受理；HTTP 5xx/unknown 与 retryable 字段的含义也需要一致，避免消费方误解成重新生成许可。

## 建议五：统一阶段事件和可解释错误，P1

提供可选服务端 onEvent/observer：load、compose、upload、submit、poll、result，以及来源/请求/返回尺寸和耗时。宿主再接入自己的日志、文件快照或监控，不由模块默认写文件。

安全错误增加可选 providerTaskId、httpStatus、已知 providerCode 与建议恢复动作。对 invalid_size 等已知错误给出明确说明，仍不向用户直接回显任意供应商响应。快照脱敏要覆盖认证头、密钥值、签名 URL、图片 Base64 与错误 cause；原始文字 LLM 输出与实际使用提示词分别记录，诊断采集需有上限和开关。

当前 451 有一次内置澄清重试。建议把这一行为写进可见策略并记录每次尝试，仍保留原提示词和安全限制；不要把它与网络未知状态或尺寸错误的重试混为一谈。

## 建议六：交付、文档和接入回归，P1

## 用户修正交付方式（2026-10-21）

用户要求：“不允许进行这样的缩放和裁切，采用的方式可以是将最短边对齐，随后均匀的裁切掉两侧的最长边多的像素的部分。除了这种裁切的方案之外，还需要有保持原图的方案的兼容”。

明确取消此前缩放补白的 contain 方案，保留原样保存模型返回图和短边对齐后长边对称裁切两种模式。来源旧图均不可覆盖。尚需确认：返回图短边不足时是否允许等比缩放，以及裁切只需匹配来源比例还是必须匹配来源精确像素。例如 1920x816 无法仅靠裁切得到 1916x821；在答案到达前，不假定允许放大或改变目标尺寸，相关规则保持待确认。本轮不修改模块业务代码或 A+ 宿主现有后处理。
