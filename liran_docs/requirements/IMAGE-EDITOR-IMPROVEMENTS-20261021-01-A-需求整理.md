## 现状与问题

现有 `normalizeApimartImageUrl` 已接受字符串 URL，并检查协议和凭据字段；但 APIMart 结果中 `data.result.images[0].url` 若为 URL 字符串数组，当前对象字段处理不会遍历该数组，导致存在有效图片 URL 时仍可能解析为无结果。

现有测试覆盖 `images` 数组里对象的字符串 `url`，没有覆盖对象内 `url` 本身为数组、数组中首项非法而后项合法等情况。该问题位于 APIMart 结果规范化，不需要改变 provider 请求、任务状态或公共接口。

## 已收敛需求

1. 继续支持现有已接受的字符串 URL 结构，保持现有调用结果一致。
2. 在经确认的结果字段路径中，允许 `url`、`image_url`、`imageUrl` 的值为字符串或字符串数组；逐个验证候选，返回首个安全有效的 HTTP(S) URL。
3. 候选为空、类型不支持、URL 格式不合法、协议不安全或包含用户名/密码时跳过该候选；如后续候选有效，应继续检查并返回该项。
4. 只解析当前 provider 合同中已确认的字段路径，不对整个响应任意递归搜寻 URL；避免把输入图、任务详情或无关字段当作生成结果。
5. 所有候选都无效时仍返回 `undefined`，由既有 provider/service 错误路径报告失败；不伪造成功、不改变错误结构、不吞掉 task ID。
6. 用脱敏的最小 fixture 表达已观察到的嵌套字段形状。除字段形状外，不伪称 fixture 是供应商未经修改的完整原始响应。
