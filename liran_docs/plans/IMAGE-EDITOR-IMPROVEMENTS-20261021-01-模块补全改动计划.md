### 5.1 模型注入

- 保留旧服务入口的 Nano Banana 2.1 / auto / 1K 行为，不直接改变所有旧调用的默认值。
- 通过新增可选通用服务或显式新入口承接模型、resolution、quality、尺寸策略等服务端配置。宿主可配置 GPT Image 2、Sunburst 或 Nano 预设，LLM 和浏览器不能覆盖模型、供应商或凭证。

### 5.2 尺寸处理的职责与配置位置（候选合同）

尺寸规则由宿主的可信服务端路线配置提供，模块负责计算和校验，适配器负责把结果编码成供应商参数。结果适配单独处理，不能因为请求尺寸合法就声称返回文件满足目标尺寸。本节是讨论中的设计细化，尚未变更公共 API。

| 部分 | 宿主输入 | 模块职责 |
| --- | --- | --- |
| 路线能力 profile | routeId、provider、model、profileVersion、已确认的 size 参数形态与范围 | 对该具体路线执行约束，不根据模型名前缀猜规则 |
| 请求策略 requestPolicy | source / fixed / provider-auto，以及合法化与超限处理选择 | 从来源或固定目标计算请求尺寸，不修改上传图 |
| 交付策略 resultPolicy | provider-native / center-crop | 原样保留返回图，或等比覆盖来源画布后居中裁切；允许等比缩放，禁止补白和拉伸 |

首批不建设全供应商能力数据库。profile 随宿主路线注入；模块可提供有来源的少量示例。每条已知限制记录来自文档、真实响应或兼容配置，注明核对日期。缺失限制代表未确认，不能解释成“不限”；也不能把模块本地解码像素上限当作供应商输出上限。

Sunburst 实测只明确证实过该路线非 16 倍数请求被拒绝；GPT Image 2 的路线约束需单独核对，不能继承为“所有 GPT 的通则”。resolution/quality 与像素 size 分开记录，1K 等档位不被当作精确宽高保证。路线尚未确认支持自定义像素时，不自动生成任意像素请求；可使用已确认的固定尺寸/auto，或由宿主显式提供试验配置，其结果不自动升级为默认能力。

### 5.3 请求尺寸计算规则（候选合同）

- 服务端实际读取来源 width/height，必须是正有限整数，并通过模块自身的字节/解码像素保护；前端显示宽高不作为权威值。
- source 使用来源宽高作为期望输出；fixed 使用宿主指定正整数宽高；provider-auto 只在路线声明支持时使用，不伪造预计返回像素。
- 对已声明步长的路线，source 策略默认做最近倍数取整，正好居中时向上；结果至少为一个正步长。宽、高分别计算，再整体校验。1916x821 配合双边步长 16 得到 1920x816，1568x672 保持不变。
- fixed 默认精确匹配，不静默取整；不合法则提交前报错。宿主若要 fixed 自动调整，应显式选择同样的取整策略并记录调整。
- 校验路线已确认的最小/最大宽高、总像素和离散尺寸集合；没有匹配合法尺寸时，默认 reject。不自动缩到另一像素预算，不自动切换模型、auto 或其他比例。后续若需要 fit-within 等降级策略，应另行设计和验收。
- width/height 的乘积应做安全整数检查；供应商允许范围与模块本地处理上限同时生效，各自标注原因。
- provider-auto 与数值 size 的编码由 adapter 负责。APIMart 可编码成宽x高字符串或 auto；通用纯函数不直接生成 HTTP 请求。

### 5.4 四类尺寸与参考流程

| 边界 | 参考行为 | 例子 |
| --- | --- | --- |
| 来源图片 | 读取当前选中不可变版本的实际像素 | 1916x821 |
| 上传图片 | 原图与可选标注合成，上传时不 resize | 1916x821 |
| 模型请求 | 按 source 策略及该路线已声明的双边步长 16 计算 | 1920x816 |
| 最终交付 | 原样模式保留实际返回值；裁切模式等比覆盖后居中裁切到来源精确宽高 | 裁切模式最终 1916x821，无补白 |

流程为：受控读取来源 → 计算并校验尺寸计划 → 原尺寸标注合成/上传 → adapter 提交输出参数 → 获得结果 → 宿主受控下载 → 可选结果适配 → 宿主追加新版本。上传图片尺寸与请求输出参数是不同字段，不能都叫 size。A+ 的普通生图和重生固定 1920x800 仍是宿主策略，不变成通用模块默认值。

### 5.5 结果处理与尺寸报告（两种行为已确认，公共 API 仍待正式合同）

可选结果工具接收宿主已经下载的字节和目标宽高，不自行访问任意 URL，也不持久化文件。先验证真实格式、解码尺寸及本地处理上限，再按策略处理：

- provider-native：保留模型返回图的原字节和实际像素，不缩放、不裁切、不补边、不重新编码，不承诺匹配来源。这里的“原样保留”指保存模型完整返回图；作为编辑来源的旧图在所有模式下均不覆盖。
- center-crop：用户已明确选择“允许等比缩放来对齐短边，再居中裁切多余长边，最终保持原图像素宽高”。按 cover 语义等比放大或缩小，保证覆盖来源画布，再居中裁去溢出内容。最终宽高严格等于选中来源，不拉伸、不补白，不保留与目标比例冲突的全部画面。

裁切模式的确定性几何规则：

1. 模型返回宽高为 W/H，来源目标宽高为 Tw/Th，统一缩放比例 s = max(Tw/W, Th/H)。选择该模式即允许 s 大于 1 时放大、小于 1 时缩小，放大不承诺增加细节。
2. 按同一比例缩放，覆盖边界按整数像素向上取整，形成 Sw = ceil(W*s)、Sh = ceil(H*s)。这些尺寸用于像素栅格及裁切矩形计算，不能通过独立拉伸两个轴来凑数。
3. 取 left = floor((Sw-Tw)/2)、top = floor((Sh-Th)/2)，裁切宽高固定 Tw/Th。奇数个溢出像素允许两侧相差 1 像素，多出的 1 像素固定在右侧或下侧。
4. 横竖方向不同时，仍按上述两个边长比值的较大者实现覆盖，不机械以数值更短的一边配对，防止出现未覆盖画布。
5. 来源尺寸、覆盖后的中间尺寸必须通过安全整数和本地处理像素上限检查；超限则保留结果并报错，不自动降质、换模式、补边或重新提交模型。

示例：返回 1920x816，来源 1916x821，s = 821/816。等比覆盖后像素外框约为 1932x821，左右各裁 8 像素，得到 1916x821。provider-native 模式则直接保存原始 1920x816，不参与这次缩放/裁切。

用户已确认新通用编辑服务默认 center-crop；宿主显式选择 provider-native 时保存完整原始返回图。旧服务入口继续保持原样结果行为，不因新默认值改变旧调用。

裁切模式必须先检查模型返回与来源的实际宽高：两条边都相同则直接返回原字节，禁止无意义缩放、裁切或重新编码；格式也不强制改为 PNG。仅尺寸不同时才执行 cover/crop，需要处理时输出 PNG。只因比例相同但像素不同，不能跳过必要的等比缩放。报告分别记录是否采样、裁切、重编码；同尺寸分支均为 false，cropRect 可为空。旧来源不覆盖，处理失败保留原任务/返回结果，不重新生图，不悄悄切换模式。

几何计算要避免浮点误差让本应对齐的一边多出 1 像素：覆盖约束边直接使用目标整数宽或高，另一边按统一比例向上取整，或使用等价安全整数比值计算。不允许分别拉伸两个轴。

请求前报告包括 routeId/profileVersion、sourceSize、uploadSize、desiredSize、requestSize、sizeAdjusted 和调整原因；auto 的 requestSize 使用明确 auto 值，预计宽高留空。结果报告再追加 providerResultSize、scaledSize、scaleFactor、finalSize、resultPolicy、cropRect、resampled 和 reencoded。不得把缩放裁切后的文件伪称模型原始返回；两份报告与任务配置一起冻结，恢复任务不按后来变更的 profile 重算原请求。

批次验收：已确认步长规则下 1916x821 请求 1920x816；1568x672 不变；半步向上；fixed 非法时拒绝而非取整；未声明自定义尺寸能力时不猜参数；最小/最大边界、总像素超限及无合法离散尺寸明确失败；来源/上传和模型请求在 HTTP 集成用例中分别断言。原样模式全字节一致；裁切模式覆盖放大/缩小、横竖方向变化、比例相同、同尺寸和奇数溢出，最终像素精确、两侧对称差不超过 1 像素、无补白/拉伸、处理报告完整，失败不重生。

## 6. 批次 C：任务状态与恢复

主要文件：`src/adapters/apimart/client.ts`、`src/core/types.ts`、`src/guidance/types.ts`、`src/guidance/server.ts`、`examples/react-express/server.ts` 与对应测试。

### 6.1 公开任务句柄

提供 submit + poll/resume，或在兼容 generate 上增加 onAccepted/resume 的组合能力。任务句柄至少关联 provider、model、providerTaskId、operationId 和非敏感路线/参数快照；不保存 API key 或认证头，也不信任客户端提供的任意任务查询 URL。

原 generate 快捷入口仍可串起提交与轮询。超时、断连、重启后，宿主可通过已保存句柄继续查同一任务，而不是再次上传/提交。旧记录缺失 taskId 时明确“不可自动恢复查询”，不补造任务号、不推断可以重新生成。

### 6.2 可行性与保证边界

模块能保证在宿主原子占位合同成立时，不因并发或自动重试重复发起无保护的提交；不能仅凭本地状态保证供应商远端恰好执行一次，也不能保证所有未知任务一定可恢复。

| 供应商能力 | 恢复路径 | 必须核实的条件 |
| --- | --- | --- |
| 支持幂等键 | 显式恢复时复用同一键及同一请求内容 | 键的作用域、有效期、参数变化行为、并发语义；超出期限不当作仍受保护 |
| 支持按客户端请求标识查询 | 使用原请求标识确认任务，再取得 taskId | 查询可见性/延迟、唯一性和未找到的含义；查不到一次不代表未受理 |
| 两者均无或尚未证实 | 无 taskId 的受理未知保持 unknown | 禁止自动重提、换操作 ID、换备用或补造任务号；可等待或核查，但不承诺能恢复 |

现有模块 adapter 没有公开幂等键或按请求查询接口，供应商是否提供这些能力仍未验证，不能把表中前两项写成既成能力。仅在能力确认且恢复策略显式允许时才复用请求；默认不自动重交 unknown。HTTP 状态码、超时、连接中断和一次空查询都不是远端没有执行的充分证明。

### 6.3 处理阶段与受理状态

流程阶段与 submissionState 分开保存，前者表示正在做什么，后者表示已知受理事实：

| 流程阶段 | 受理状态 | 持久化边界/可用动作 |
| --- | --- | --- |
| prepared | not_submitted | 来源、提示词、路线、尺寸与请求标识冻结，尚未允许网络派发 |
| dispatching | unknown | 必须在提交网络请求前原子写入；此后不能因进程重启直接当作未提交 |
| accepted / polling | submitted | 取得并持久化经验证的 taskId，允许查询原任务 |
| result_ready | submitted | 有效结果引用已保存，尚未追加版本，不能重新生成 |
| saving | submitted | 正在幂等追加版本，失败只重试保存 |
| completed | submitted | 返回已保存版本，重复请求不再提交/追加 |
| rejected | not_submitted | 必须有明确未受理证据，并记录终止原因 |
| outcome_unknown | unknown | 未获得足够受理证据，仅按第 6.2 节能力恢复，否则保留未知 |

旧三态可继续作为兼容字段，不能用它替代新阶段。宿主锁的租期到期不等于远端任务不存在；不得把 dispatching/outcome_unknown 自动重置成 prepared。

### 6.4 状态与动作

| 已知事实 | 保留状态 | 允许的恢复动作 |
| --- | --- | --- |
| 尚未派发，或有明确未受理证据 | not_submitted | 在用户/宿主显式重试时重新提交 |
| 已进入派发，尚无可靠结果 | unknown | 检查状态；不能自动重复提交 |
| 已获得任务号并确认受理 | submitted | 继续轮询原任务 |
| 已得到有效图片结果但保存失败 | submitted，带结果引用 | 仅重试保存 |
| completed 但无有效图片 | submitted，带 taskId 和错误 | 查询/诊断原任务，不冒充成功或重生 |

调用生成器前必须持久化运行中/受理未知边界；不再在生成进行中留下可直接重提的 not_submitted。HTTP 408、提交连接中断、部分 5xx 都不能作为确定未受理的证明。retryable 的语义必须与具体动作一致，不能让“可查询”被消费方理解成“可再次生成”。

由宿主提供按 principal/operationId 的原子占位和状态更新，必要时按 sourceId 排斥并发操作；进程内锁不能代替跨进程/重启后的持久化。示例和文档必须展示这些要求，而不是仅声明接口可注入。版本追加仍按 operationId 幂等。

状态写入失败在派发前应停止提交；派发后状态保存失败不得假设没有任务，也不得自动重放。凭证由恢复时的受控服务端环境读取。

批次验收：宿主原子占位使同 operationId 并发不重复派发；无幂等/查询能力、已受理但丢失 taskId 时保持 unknown 且不自动重提；幂等窗口过期和查询暂不可见不能误判未受理。模拟 prepared、dispatching、accepted、result_ready、saving 各位置崩溃；恢复查询不重交，恢复保存不重生，跨用户不能访问任务或结果。供应商远端恰好一次不是无条件验收承诺。

## 7. 批次 D：prompt-only 指导模式

主要文件：`src/guidance/types.ts`、`src/guidance/prompt.ts`、`src/guidance/validation.ts`、`src/guidance/server.ts` 及 guidance 测试。必要时新增显式入口，保持旧入口的严格合同。

- 输入：服务端解析的来源完整提示词及本轮指导，来源身份在 LLM 调用外保留。
- 输出：完整可直接生图的新提示词，不要求 updatedPlan、summary 或额外方案组装。用户明确修改优先于旧提示词冲突的创意设定，其余内容尽量保持。
- 非空意见只调用一次改写；空意见零次改写。成功文本直接交给生图器，重试生成复用已冻结文本，不再调用改写。
- 支持完整纯文本、已知旧 JSON 和围栏；仅对完整闭合 JSON 后的纯格式噪声容错。空内容、截断 JSON、第二份冲突内容明确失败。
- 输入非空/长度、来源鉴权、任务身份与安全规则继续存在。旧 plan-and-prompt 模式保留原方案校验，不能通过新模式偷偷改变旧客户行为。
- 模板和 parser 有独立版本，快照区分原始输出与实际使用文本；不新增自动纠错 LLM，也不回退旧提示词冒充修改成功。

批次验收：男性改女性的完整文本无需 updatedPlan 即可生图；纯文本、围栏和允许的格式尾噪可用；截断/冲突输出不生图；旧严格模式回归仍通过；失败重试次数符合 C 批次约束。

## 8. 批次 E：事件、错误与脱敏

提供可选服务端 observer/onEvent，覆盖 load、compose、upload、submit、poll、result、rewrite 等阶段，携带操作身份、开始/结束/失败、耗时、尺寸和安全诊断摘要。宿主自行接入磁盘快照或监控，不默认在模块中创建数据目录。

安全错误可增加 httpStatus、已知 providerCode、providerTaskId 和建议恢复动作；已知尺寸错误给出明确说明，未知错误不向用户直出原始 body/cause。原有安全字段保留兼容。

可选诊断事件与保证状态正确的持久化回调分离：观察器失败不得触发重新生成或丢失已受理信息；必要状态写入失败按 C 批次处理。原始 LLM 输出采集默认最小化，详细诊断由宿主显式开启、限长并脱敏。

脱敏覆盖实际凭证值、Authorization/cookie、签名 URL 参数、图片 Base64 和错误 cause。不得只靠键名黑名单。每次 provider 尝试均可关联记录；既有 451 澄清行为需明确兼容及显式策略，不借机放宽内容安全要求，也不与未知状态重交混用。

## 9. 批次 F：交付与文档

1. 确认已有画笔修复与 0.1.1 的基线，协调 package/lock 版本，不覆盖当前未提交改动。
2. 公共扩展建议按下一功能版本评估；若无法保持旧行为，采用显式新入口或正式迁移，不只改版本号掩盖不兼容。
3. 使用新的独立产物目录验证打包，不清理现有包/历史文件；通过 npm pack dry-run 后做干净 tarball 消费测试。
4. 使用同一个干净 tarball，分别在 ESM 的 .mjs 文件中 import、CommonJS 的 .cjs 文件中通过异步 import() 加载 core/server/guidance 等声明支持的入口；React/CSS 用前端打包器单独验证，不能用 Node 直接加载 React CSS 代替。无需支持同步 require()，不因其失败扩大为双构建。
5. 保持 browser boundary，确认前端无 Sharp、provider 或凭证依赖。
6. 更新 README、架构方案、接入指南、错误/尺寸/恢复示例与测试用例；区分独立 mock、A+ 局部接入和完整服务接入事实。
7. A+ 宿主替换和真实模型质量验收列为后续独立接入任务，不在模块完成后自动修改或部署宿主。

## 12. 验证、回退与交接

开发时每个行为先写失败用例，再最小实现并复测。按批次运行有意义的专项测试，收口时运行 npm test、npm run build、npm run harness:check、npm run harness:test 与打包消费检查。不得将本轮旧基线测试通过写成新增功能已实现。

回退采用旧入口和新能力显式 opt-in：宿主可继续旧服务，不撤销已完成任务；已受理任务始终按原句柄/路线查询。新增结果处理不批量改写旧图片；pending 结构变更需兼容读取或显式迁移，迁移前另行确认，不删除历史记录。Git 回退不使用 reset --hard、clean 或强推。

本计划不承诺固定工期。阶段交接必须记录实际 diff、命令、退出结果和限制；真实模型联通/质量、宿主接入、发布、Git 提交推送分别按后续明确授权执行。当前先交付计划，后续再进入正式开发合同确认。
